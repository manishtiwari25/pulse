Why teams need PULSE

Many people and tools should not mean many versions of the truth.

A feature can move through tickets, chat, planning documents, coding agents, pull requests, and several developers. Without a shared record, each person and tool keeps only part of the story.

Without PULSE

The reasoning becomes fragmented.

Developer A Tickets Team chat IDE agent Developer B Planning docs
  • Plans conflict because they live in separate systems.
  • Code explains what changed, but not why it changed.
  • Rejected options and important constraints disappear.
  • Handoffs depend on the memory of the original developer.

With PULSE

The team gets one shared engineering history.

  • Every tool reads and writes through the same control plane.
  • Each feature points back to its context, decision, and plan.
  • Reviews have a clear audit trail and verification evidence.
  • New developers and agents can continue without guessing.

PULSE does not replace tickets, chat, or planning tools. It keeps the durable engineering truth beside the code.

Context -> Options -> Decision -> Plan -> Feature -> Code -> Verification -> Learning

A visible decision tree lets anyone trace why a feature exists and how the team proved it works.

The lifecycle

One continuous rhythm from idea to learning.

Each PULSE stage produces durable information that the next stage can use. The cycle repeats as the repository and product evolve.

01

Understand

Read product context, stack constraints, architecture, prior choices, and durable memory.

02

Decide

Record important product and technical choices with their reasons and tradeoffs.

03

Plan

Turn the desired outcome into ordered steps, acceptance criteria, and verification.

04

Specify

Describe the behavior users and systems should receive before implementation begins.

05

Build & verify

Use focused workflows and prompts, then prove the result with real repository checks.

06

Learn

Keep reusable patterns, product rules, and mistakes so the next cycle starts smarter.

Agent-driven rollbacks

Every change starts with a safe way back.

PULSE makes recovery part of the plan, not an improvised command after something breaks. Agents can reverse their own isolated work, preserve everyone else's changes, and prove the known-good state has returned.

Baseline -> Change -> Verify
If unsafe or failing -> Scoped rollback -> Recovery verified
01

Plan before changing

Record the baseline, trigger, reversal steps, state-safety limits, and recovery checks.

02

Reverse only this task

Use precise inverse changes. Preserve user work, shared history, deployments, and data.

03

Prove recovery

Rerun the baseline checks and keep an audit record of the trigger, actions, and final state.

Safety boundary Agents stop for an approved runbook or explicit permission when production, migrations, data, shared history, or unrelated work could be affected.

Proportional lifecycle tiers

Paperwork that matches the size of the change.

One universal gate makes the human the bottleneck on small work. PULSE asks the agent to declare a tier and a one-line reason at the start of every change, then produces only the artifacts that tier needs. When in doubt, go up one tier.

Request -> Declare tier + reason -> Only that tier's artifacts -> Verify -> Delivery mark
If the work outgrows its tier -> Stop and redeclare higher -> Add that tier's artifacts
T0

Polish and repair

Copy, spacing, colors, icons, focus order, a bug with a reproducing test, a doc fix. No control-plane file; an in-session rollback checklist plus tests. Standing autonomy, same-day target.

T1

Behavior inside an accepted decision

A page, state, or flow an Accepted ADR already allows. One work unit - plan, spec, and prompt in a single file that names its controlling ADR. Standing autonomy inside that boundary, two-day target.

T2

Real decisions

Money, auth, identity, data, privacy, migrations, dependencies, deploy, publish, security posture, or any surface no ADR covers. Full ADR, plan, spec, and prompt chain with explicit human approval.

Hard stops never move Destructive or irreversible actions, production, deploy, publish, merge, credentials, hosted-data deletion, broad auth, billing, or data migrations, infrastructure, major dependency upgrades, policy-sensitive security, purchases, and ambiguous evidence need explicit approval in every tier. No new Proposed ADR opens in an area while another is unbuilt there; every ADR carries a delivery mark, a quarterly prune refreshes it, and a read-only report shows proposed-to-delivered days.

What can go wrong

Spec-driven development has known failure modes. PULSE names them.

Writing things down before code changes is not free, and coding agents do not read the way people do. These pitfalls are documented in published studies and field reports. Each card says what PULSE does about it and what still needs a human.

01

Paperwork out of proportion

A small bug becomes four user stories and sixteen acceptance criteria. PULSE sizes artifacts by tier: a Tier 0 fix needs none. A human still checks the tier was honest.

02

Bigger context, worse agent

Model accuracy degrades as input grows, even with perfect retrieval. PULSE routes agents to the few relevant files and exact source ranges instead of the whole control plane.

03

Reviewing Markdown instead of code

Tools generate piles of repetitive spec files, and developers feel faster while measurements say otherwise. Tier 1 is one file; lead time is measured, not assumed.

04

Written but never built

Agents skip instructions, and decisions pile up unbuilt. Every ADR carries a delivery mark, a work-in-progress limit blocks new proposals over unbuilt ones, and a quarterly prune reconciles reality.

05

Gamed checks

Told to make tests pass, an agent may edit the tests or the verifier. PULSE verifies with commands that already exist, requires reproducing tests, and reviews test diffs like code.

06

Spec drift and false confidence

Specs go stale, the same spec yields different code, and thick documents feel like control. Decisions retire visibly, rollback is planned before the first edit, and review demands evidence.

Evidence, not vibes The guide cites Birgitta Böckeler's Kiro, Spec Kit, and Tessl trial, the Thoughtworks Radar, Chroma's context-rot study, METR's developer productivity trial and its update, the 2025 Stack Overflow survey, Kent Beck, OpenAI's reward-hacking report, and GitHub's Spec Kit launch - with what PULSE cannot fix stated plainly.

Token-aware delegation

Know the likely effort before handing over the task.

The advisor starts from task signals and can use an explicitly supplied history file to limit outlier influence and improve confidence.

It never invents provider pricing. A monetary comparison appears only when the user supplies human time/rate and an agent token rate.

The control plane

A home for every kind of engineering knowledge.

PULSE uses a predictable `docs/` map. Agents and people always know where to read before acting and where to save what matters.

context/Product, users, stack, constraints, and current state.
architecture/System shape, boundaries, data, and deployment.
decisions/ADRs for choices that need durable reasons.
features/Behavior and outcomes before implementation.
plans/Ordered work, acceptance criteria, and checks.
prompts/Reusable, model-agnostic execution instructions.
skills/Portable Agent Skills and bundled helpers.
workflows/Repeatable procedures for common engineering work.
memory/Durable rules, patterns, lessons, and mistakes.
usage/Frozen history from the retired accounting experiment.
